# Large and binary job results

SDK 0.7.0 adds an optional result-file extension alongside the existing UTF-8
256 KiB APIs. A trusted command registers a generated file with
`job.addBinaryArtifact({id, path, label?})`. The host pins its SHA-256 and length;
clients read bounded chunks or use the Node downloader to resume and verify a
complete local file. The extension has no runtime dependencies.

## Enable and register

Enable both `jobs: true` and `binaryArtifacts: true` in `createWorkspaceServer`.
Both default to false. Use the normal explicit token, operator notice, reviewed
plugin artifact pin, and effective `workspace.read` grant. Binary registration
also works with a read-only workspace containing results already generated by
the operator's configured tool.

```js
const server = await createWorkspaceServer({
  root, workspaceId, token, notice,
  plugins: [{plugin, artifactSha256}],
  grants: ['workspace.read'],
  jobs: true, binaryArtifacts: true, writable: false,
});
```

Inside the configured plugin:

```js
context.registerCommand({id: 'collect', title: 'Collect trace'}, async (_, {job}) => {
  if (!job) throw new Error('Start this command as a job');
  const artifact = await job.addBinaryArtifact({
    id: 'trace', path: 'outputs/trace.fst', label: 'Simulation trace',
  });
  return {artifactId: artifact.id};
});
```

The file must already exist under the selected workspace. Registration streams
its bytes through SHA-256, using a 64 KiB buffer and a maximum 30-second port
operation. The Node host rechecks root, parent paths, file identity, size and
timestamps around reads. Protected paths, traversal, symlinks, hardlinks and
non-regular files are rejected. Subsequent source changes produce `conflict`.
This is a reference to the original file, not an immutable copy.

Binary and text results share 16 registration slots and an ID namespace per job.
Binary references are returned by the new list API; they are not inserted into
the old `JobSnapshot.artifacts` array. Registration emits an ordinary log event,
so existing v1 snapshot/event consumers continue working.

## Read a registered result

Use an already connected, authorized client and an existing job ID. Discovery
does not start a job or grant permission.

```js
const capabilities = await client.getBinaryArtifactCapabilities();
if (!capabilities.enabled) throw new Error('This host has not enabled binary results');
const reference = await client.getJobBinaryArtifact(jobId, 'trace');
const first = await client.readJobBinaryArtifactChunk(reference, 0);
console.log(first.offset, first.nextOffset, first.eof);
```

`listJobBinaryArtifacts(jobId)` returns `{jobId, scope, artifacts}`.
`getJobBinaryArtifact(jobId, artifactId)` returns `{jobId, scope, artifact}`,
where `artifact` is `{id, path, revision, byteLength, label?}`. Keep this whole
reference when resuming; it binds the file to a job, workspace and host generation.

`readJobBinaryArtifactChunk(reference, offset, {length?, signal?, timeoutMs?})`
returns that identity plus `{offset, nextOffset, eof, data, sha256}`. `data` is
canonical base64; `sha256` covers that chunk. The client validates identity,
revision, exact requested range and chunk digest. EOF has `nextOffset` equal to
the file length. Reading exactly at EOF returns an empty chunk, including for
an empty file. Offsets beyond EOF are invalid.

Use `decodeBinaryArtifactData(chunk.data)` from `/artifacts` for a `Uint8Array`.
These chunk APIs work in Node and compatible browser clients. A chunk checksum
does not prove the complete file matches `artifact.revision`; browser consumers
must hash their assembled or streamed output before accepting it.

## Download, interrupt and resume in Node

```js
import {downloadJobBinaryArtifact} from '@altifigence/dds-plugin-sdk/workspace-node';

const reference = await client.getJobBinaryArtifact(jobId, 'trace');
const receipt = await downloadJobBinaryArtifact(client, reference, {
  destination: absoluteDownloadPath,
  resume: true,
  signal: abortController.signal,
  onProgress({receivedBytes, totalBytes}) {
    console.log(receivedBytes, totalBytes);
  },
});
console.log(receipt.verified, receipt.revision);
```

The caller chooses an absolute destination in an existing real directory. The
downloader writes `destination + '.dds-part'`. With `resume: true`, it rehashes
that file's existing bytes and requests only the missing suffix. Without explicit
resume, an existing partial file is a conflict. A successful result includes
`{path, revision, byteLength, resumedBytes, verified: true}`.

Whole-file SHA-256 must match both the received stream and a final streaming read
of the staging file before publication. The helper never buffers an entire file.
It refuses an existing final destination, linked staging files and a symlink
parent. Publication uses an exclusive hardlink followed by unlinking the staging
name, requiring a filesystem with hardlink support, such as NTFS or ext4. The
partial and final file reside in the same directory.

Cancellation, transport errors, source changes and checksum failures leave the
partial file for explicit retry or inspection. They do not automatically restart
the command or remove earlier bytes. A corrupt prefix must be discarded or a new
destination chosen. `onProgress` is synchronous and reports `verified: false`;
only the final receipt confirms verification. The total `timeoutMs` defaults to
30 minutes (also the maximum). `requestTimeoutMs` defaults to 5 seconds, with a
30-second maximum per HTTP request.

Disconnect/reconnect invalidates an in-flight download. After explicit reconnect
to the same host generation, call the helper again with the saved reference and
`resume: true`. A host restart, expired job, changed generation or revoked plugin
prevents reuse. Jobs still use their existing in-memory retention: 15 minutes
from the terminal job's last event, cleaned on access. Cancelling a job does not
erase already registered files; those may be partial tool output and are not
proof that the command succeeded.

The Node filesystem checks are not an OS sandbox or a lock against a hostile
process that can rewrite files between checks. Store downloads in a directory
controlled by the caller. As with existing writes, final filesystem operations
may complete even if cancellation arrives during publication; inspect the paths
before deciding whether to retry.

## Bounds and compatibility

| Bound | Value |
| --- | --- |
| Registered binary file | 1 GiB maximum |
| Decoded bytes per chunk | 64 KiB maximum |
| Binary capture/read operations | 4 per host/workspace |
| Concurrent Node downloads | 4 per process, distinct destinations |
| Result registrations | 16 per job, shared with text results |
| Text file/read/edit APIs | Unchanged: 256 KiB UTF-8 |

Base64 adds encoding overhead; the reference HTTP transport keeps bounded JSON
responses rather than allocating or returning the whole file. The optional wire
methods are `artifacts.capabilities`, `artifacts.list` and `artifacts.read` on the
existing authenticated endpoint. v1 hello, jobs, manifest and permission shapes
remain unchanged. Binary transfer needs support on both ends and explicit host
opt-in; supplied external plugin hosts are not enabled by the HTTP reference host.

Known SDK hosts before 0.7 report disabled locally without an unknown-method
probe. Other hosts may return a correctly correlated `unsupported` discovery
reply. Malformed replies, authentication/permission errors and transport failures
are errors; there is no fallback to text reads or another execution path.
Discovery is cached only for the current connection and cleared on revocation
or reconnect. Custom workspace ports implement `captureBinaryFile()` and remain
responsible for safe source isolation and coherent pinned reads.

Run `npm run example:artifacts` for a real 2 MiB binary transfer with cancellation,
reconnect and suffix-only resumption. `npm run benchmark:artifacts` repeats that
path with 8 MiB and reports request counts and JSON response bytes. Both generate
and remove their own temporary files. SDK capabilities and DDS product integration
are released and verified separately.

## 한국어

0.7.0은 기존 텍스트 API의 256 KiB 제한을 유지하고 별도 바이너리 작업 결과를
지원합니다. 운영자가 `jobs: true`, `binaryArtifacts: true`를 켜고 플러그인에
`workspace.read`를 허용해야 합니다. `job.addBinaryArtifact()`는 이미 생성된
파일을 상대 경로·SHA-256·크기로 등록하며 최대 1 GiB를 지원합니다.

`getJobBinaryArtifact()`로 작업·워크스페이스·호스트 세대가 포함된 참조를 받고,
`readJobBinaryArtifactChunk()`로 최대 64 KiB씩 읽습니다. Node의
`downloadJobBinaryArtifact()`는 `.dds-part`에 저장하고 전체 수신 데이터와
실제 임시 파일의 SHA-256을 검증한 뒤 최종 파일을 만듭니다. 기존 최종 파일은
덮어쓰지 않습니다. 브라우저에서 조각 API를 사용하면 전체 파일 해시 검증은
소비자가 별도로 수행해야 합니다.

중단 후 같은 호스트 세대에 다시 연결하고 저장한 참조와 `resume: true`를
사용하면 기존 임시 파일을 다시 해시하고 남은 부분만 요청합니다. 손상된
임시 파일은 최종 결과로 확정되지 않습니다. 재시작·작업 보관 만료·파일 변경·
권한 회수는 자동으로 우회하지 않습니다. 진행률 콜백은 동기식이며 완료 반환값의
`verified: true`가 전체 검증 성공을 뜻합니다. 결과는 기존 작업 보관 기간
안에서만 접근할 수 있고, 실행 영구 보관이나 DDS 제품 UI를 추가하지 않습니다.
